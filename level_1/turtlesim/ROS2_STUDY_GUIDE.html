01 · ORIENTATION

먼저 전체 구조를 보자

ROS 2는 하나의 거대한 프로그램이 아니라, 역할별 노드(node)들이 이름 있는 통신 채널로 협력하는 로봇 소프트웨어 구조입니다.

핵심 데이터 흐름일반 연결선택/보조 연결외부 도구·API

핵심 질문

“어떤 노드가 어떤 메시지를, 어떤 규칙으로, 얼마나 자주 주고받는가?”를 추적하면 ROS 2 그래프를 읽을 수 있습니다.

과제의 중심

Pose를 받아 거리로 계산하고 Float64로 발행합니다. 제어는 Twist를 보냅니다.

관찰 도구

ros2 node/topic/service/action, rqt_graph, RViz2, rosbag, pytest로 상태를 확인합니다.

02 · CORE CONCEPTS

ROS 2를 이루는 9개의 관절

용어를 외우기보다 “상황에 맞는 통신 형태”와 “실행을 담당하는 주체”를 구분하세요.

1. Node · 노드

한 가지 책임을 수행하는 실행 단위입니다. Python은 class X(Node), C++는 class X : public rclcpp::Node로 만듭니다.

2. Topic · 토픽

연속 데이터를 흘려보내는 이름 있는 채널입니다. publisher는 보내고 subscriber는 받습니다. /turtle1/pose 같은 절대 이름과 turtle_dist 같은 상대 이름이 있습니다.

3. Service · 서비스

짧은 요청-응답입니다. 순간이동·펜 설정·spawn처럼 한 번 요청하면 결과가 돌아오는 작업에 적합합니다. 과제는 call_async를 사용합니다.

4. Action · 액션

오래 걸리는 goal을 실행하며 feedback을 보내고 cancel할 수 있습니다. 회전·다각형 주행처럼 진행률이 필요한 작업에 적합합니다.

5. Interface · 인터페이스

.msg는 데이터, .srv는 request/response, .action은 goal/result/feedback을 정의하는 자료형 계약입니다.

6. Executor · 실행기

timer·subscription·service·action callback을 꺼내 실행합니다. rclpy.spin 또는 rclcpp::spin이 대표적인 대기 루프입니다. 현재 callback 안의 동기 대기는 교착을 만들 수 있습니다.

7. QoS · 통신 품질

Reliability(전달 신뢰성), Durability(늦게 온 구독자에게 과거 값을 줄지), History/Depth(버퍼 크기) 정책입니다. 양 끝의 호환이 맞아야 통신됩니다.

8. Parameter · 파라미터

실행 중 바꿀 수 있는 설정값입니다. publish_rate, warn_distance는 YAML/launch로 주입하며 잘못된 rate는 5.0으로 복구합니다.

9. Package / Workspace

package는 빌드·의존성·설치 단위, workspace는 여러 package의 집합입니다. colcon은 DAG 순서로 빌드하고 source install/setup.bash가 overlay를 등록합니다.

통신 형태를 고르는 기준

질문선택이 과제의 예
계속 흘러오는 센서/상태인가?Topic/turtle1/pose → 거리 계산
짧은 요청에 즉시 답하는가?Serviceteleport, set_pen, spawn, clear

03 · ASSIGNMENTS 01—10

문제별로 무엇을 배웠는가

각 문제는 “빌드 → 실행 → 통신 → 관찰 → 검증”이라는 하나의 개발 주기를 구성합니다.

문제 1 · C++ 번역 단위, 컴파일, 링크, CMake

선언(motor.hpp)과 구현(motor.cpp)을 분리하고 main.cpp가 사용합니다. g++ -c는 object 파일을 만들고 링크가 실행 파일로 묶습니다. 구현을 링크하지 않으면 undefined reference입니다.

g++ -Wall -std=c++17 -c motor.cpp
g++ -Wall -std=c++17 -c main.cpp
g++ main.o motor.o -o motor_demo
./motor_demo
# drive_motor started

cmake -S . -B build
cmake --build build --verbose

CMake는 수정된 번역 단위만 다시 컴파일하는 증분 빌드를 제공합니다.

문제 2 · C++ 다형성, 소유권, 가상 소멸자

Sensor의 순수 가상 read()는 센서별 구현 계약입니다. vector<unique_ptr<Sensor>>에 Lidar/Imu를 담으면 부모 타입으로 다형성 순회가 됩니다. virtual ~Sensor()가 있어야 부모 포인터 삭제 시 자식부터 소멸합니다. RAII(자원 수명을 객체에 묶는 방식)는 누수를 줄입니다.

cmake -S cpp_basics/sensors -B cpp_basics/sensors/build
cmake --build cpp_basics/sensors/build
./cpp_basics/sensors/build/sensor_demo
# lidar read=1.2
# imu read=0.03
# near_goal_count=1
# clamp_speed=1 clamp_pixel=255

문제 3 · rclpy 상태 발행·감시·정사각형 주행

distance_publisher는 /turtle1/pose를 구독해 최신 Pose를 저장하고 timer로 5 Hz마다 /turtle_dist에 std_msgs/msg/Float64를 발행합니다. 거리 공식은 sqrt((gx-x)²+(gy-y)²)입니다. monitor는 기준 초과를 경고하고 square_driver는 선속도/각속도를 번갈아 보내며 종료 시 zero Twist를 보냅니다.

ros2 run turtlesim turtlesim_node
ros2 run turtle_py distance_publisher
ros2 run turtle_py distance_monitor --ros-args -p warn_distance:=3.0
ros2 run turtle_py square_driver
ros2 topic hz /turtle_dist

문제 4 · rclpy ↔ rclcpp 교차 언어 통신

호환성의 기준은 언어가 아니라 이름·인터페이스 타입·QoS입니다. Python publisher와 C++ monitor가 같은 /turtle_dist, Float64, depth 13이면 통신합니다. create_timer와 create_wall_timer는 역할이 같은 API입니다.

문제 5 · Service / Action과 교착

service_client는 teleport_absolute, set_pen, spawn, clear를 비동기 호출합니다. rotate_client는 goal, feedback, cancel을 보여줍니다. SingleThreadedExecutor에서 callback 안의 동기 대기는 응답 callback 실행을 막을 수 있으므로 call_async와 spin이 안전합니다.

문제 6 · 사용자 정의 인터페이스

Waypoint.msg는 x, y, tolerance, label을, WaypointList.msg는 Header와 waypoint 배열을 가집니다. SetGain.srv는 kp/ki/kd request와 success/message response, DrawPolygon.action은 goal/result/feedback으로 구성됩니다.

ros2 interface show turtle_interfaces/msg/WaypointList
ros2 interface show turtle_interfaces/action/DrawPolygon
ros2 action send_goal /draw_polygon turtle_interfaces/action/DrawPolygon "{sides: 4, side_length: 1.0}"

문제 7 · QoS 진단

Best Effort는 최신 데이터를 빠르게, Reliable은 전달을 보장하려 합니다. Transient Local은 publisher가 저장한 마지막 값을 late-joiner에게 전달합니다. 과제는 waypoint 3개 수신과 depth 1 버퍼의 동작을 확인합니다.

토픽정책이유
/turtle1/poseBest Effort / Volatile최신 센서 스트림
/turtle1/cmd_velReliable / Volatile제어 명령 손실 방지
/waypointsReliable / Transient Local늦게 온 노드도 경유점 필요
/turtle_distReliable / Volatile계산 결과 스트림

문제 8 · colcon workspace

ros2_ws/src에는 turtle_interfaces, turtle_py, turtle_cpp가 있습니다. package.xml 의존성 DAG(방향성 비순환 그래프)에 따라 interface가 먼저 생성되고 노드가 빌드됩니다. --symlink-install은 Python 수정 확인을 편하게 합니다.

문제 9 · launch, YAML, namespace

turtle_system.launch.py는 turtlesim, publisher, monitor, action server를 한 번에 띄웁니다. YAML 기본값은 launch argument로 덮어쓰며 namespace는 여러 로봇의 이름을 격리합니다.

ros2 launch turtle_py turtle_system.launch.py publish_rate:=5.0 warn_distance:=1.0
ros2 run turtle_py distance_publisher --ros-args -r __ns:=/turtle2
ros2 param get /distance_publisher publish_rate

문제 10 · TF, RViz2, rosbag, pytest

TF(Transform)는 좌표계 사이 위치·방향 관계입니다. broadcaster는 world → turtle1을 만들고 waypoint는 Marker로 보입니다. RViz2 Fixed Frame은 world입니다. rosbag은 토픽을 저장/재생하고 pytest는 거리·각도 정규화·tolerance 경계를 검증합니다.

ros2 bag record -o bags/turtle_run /turtle1/pose /turtle_dist
ros2 bag play bags/turtle_run
PYTHONPATH=src/turtle_py pytest -q src/turtle_py/test
# 6 passed
04 · ROBOTICS LENS

코드 뒤의 로봇공학

turtlesim은 실제 로봇 소프트웨어의 축소판입니다.

좌표와 자세

2D 위치는 (x,y), 방향은 θ입니다. 자세(pose)는 위치와 방향을 합친 상태입니다. 목표 방향은 atan2(gy-y,gx-x)로 구하고 각도 오차는 [-π,π]로 정규화해야 가장 짧은 회전을 고릅니다.

Twist와 속도

Twist는 선속도(linear velocity)와 각속도(angular velocity)를 담습니다. linear.x는 전진, angular.z는 평면 회전입니다. 정지는 모든 속도를 0으로 발행합니다.

정사각형 주행의 운동학

전진 시간과 회전 시간을 조합해 궤적을 만듭니다. 실제 로봇에서는 바퀴 반지름, 휠 간격, 미끄러짐, 제어 주기 오차 때문에 완벽하지 않습니다.

Waypoints와 경로 계획

waypoint는 갈 위치 목록입니다. tolerance는 도착 판정 반경입니다. planning은 순서/경로, control은 현재 pose에서 다음 점으로 낼 속도를 결정합니다.

PID의 직관

PID는 오차에 비례하는 P, 오차를 누적하는 I, 오차 변화율을 보는 D 제어입니다. kp/ki/kd는 반응의 세기를 조정하며 실제 시스템에서는 잡음과 windup도 고려합니다.

안전한 로봇 프로그램

잘못된 goal은 거부하고, 취소 시 정지하며, 종료 시 zero Twist를 보냅니다. 빈 waypoint는 경고하고, 음수 tolerance는 예외를 냅니다.

05 · HANDS-ON PATH

처음부터 끝까지 실행하는 순서

모든 터미널에서 ROS 환경을 source해야 합니다.

  1. 환경: Ubuntu 22.04, ROS 2 Humble, turtlesim/RViz2/rqt_graph/tf_transformations/colcon/pytest.
  2. 빌드: cd level_1/turtlesim/ros2_ws → source /opt/ros/humble/setup.bash → colcon build --symlink-install → source install/setup.bash.
  3. 기본 그래프: turtlesim, distance_publisher, distance_monitor, square_driver를 각각 실행.
  4. 관찰: node list → topic list → pose echo → topic hz → topic info --verbose.
  5. 확장: service/action, custom interface, triangle/square/hexagon goal.
  6. 도구: tf_marker_broadcaster → rqt_graph/RViz2 → rosbag record/play.
  7. 검증: pytest 6 passed와 의도적 실패 검출을 확인.

06 · DEBUGGING

메시지가 안 보일 때의 사고 순서

그래프의 존재, 이름, 타입, QoS, 주기를 차례로 좁힙니다.

1 · 노드가 있는가?

ros2 node list로 publisher/subscriber가 실행됐는지 확인합니다. 없으면 source, package 설치, 실행 파일 이름을 점검합니다.

2 · 이름·타입이 같은가?

ros2 topic list, ros2 topic type /turtle_dist로 이름과 타입을 확인합니다. relative name은 namespace로 달라집니다.

3 · QoS가 맞는가?

ros2 topic info /turtle_dist --verbose로 Reliability, Durability, depth를 비교합니다.

증상 → 원인 가설

echo가 비어 있음publisher 미실행, 이름/namespace, QoS 비호환
0 Hztimer 오류, Pose 미수신, early return
action 거부입력 검증 실패, server 미실행
RViz marker 없음Fixed Frame/TF/frame_id 문제
서비스 멈춤server 미실행 또는 callback 안 동기 대기

품질 체크

  • 빌드가 재현되는가?
  • 토픽 타입/QoS가 문서화됐는가?
  • 잘못된 입력이 안전하게 처리되는가?
  • 취소·종료 시 로봇이 정지하는가?
  • 정상/실패 테스트가 모두 있는가?
  • 실행 증거가 남아 있는가?
